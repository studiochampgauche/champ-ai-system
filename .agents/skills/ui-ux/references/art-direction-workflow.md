# From a minimal brief to a considered visual direction

Use this workflow for new websites, demos and substantial visual redesigns. A subject, one-page or multipage requirement, and languages can be enough to begin a demo. Take responsibility for the remaining design decisions; do not turn a minimal brief into a compulsory questionnaire or an approval at every checkpoint. For a small fix, preserve the established direction and inspect only the affected experience.

## 1. Establish the working brief

Infer a plausible audience, its main task, the information needed to act and a suitable tone. Note these assumptions briefly alongside the requested page structure and languages. For a fictional demo, create specific, coherent illustrative content. Do not invent real testimonials, credentials, project outcomes or business commitments. Ask only for information essential to correctness or a decision that genuinely belongs to the user.

Preserve explicit architecture, brand, content, ornament and interaction constraints. The workflow does not authorize extra dependencies, product directories, a new framework or a larger feature scope.

## 2. Select positive reference principles

Start with the user's current references and the [selected BYQ profile](approved-design-references.md). Reuse its observations; choose one primary reference suited to the content and add a supporting example only for a distinct question. There is no minimum reference count or source-diversity quota. Inspect only the actual pages or states needed beyond existing evidence, not all nine templates or every breakpoint again.

Awwwards rankings, winners and gallery feeds are not a default research step. Expand discovery only if the user requests it or the selected library cannot answer a named question about required content or behavior. State that gap briefly, prefer a targeted BYQ lookup, and use another source only if needed. Wanting more inspiration, novelty or an exact industry match is not a sufficient gap. Award status alone does not establish fit; newly found examples do not become user-approved preferences.

Use known preview routes directly. If a preview opens on a sales landing or page collection, follow a suitable Home variant or interior-page link; a purchase button can remain in its header. Record the exact route and distinguish reused notes, fresh visual observations and tested interactions. Identify useful hierarchy, type/media proportions, density and component relationships, plus what is unsuitable for this brief.

Stop researching once the available evidence supports these design decisions and proceed to rendered comparison. Reopen research only for a concrete unresolved issue; do not perform a full audit of reference sites before designing. The completed product still requires the main skill's full validation.

A liked reference does not authorize copying its branding, code or assets, or overriding the user's rules about decorative arrows or other treatments. Borrow principles, not a complete visual recipe. Reference notes are consultable memory, not model training or a guarantee of taste.

## 3. Compare small rendered alternatives

Before repeating one design throughout the site, render a small number of materially different compositions, usually two. Change content hierarchy, grouping, image use or reading density; a font or palette swap alone is not an alternative.

Keep the comparison proportionate. Lightweight HTML/CSS sketches or alternate compositions in the existing preview are sufficient. Use representative copy and realistic media framing. Do not generate raster mockups as a substitute for layout, build a second full application, or install tools solely for this comparison. Use the authorized project structure without mandating a new directory scheme.

Compare at equivalent desktop and mobile viewports. Select the stronger direction autonomously for the audience's task and the user's preferences. Briefly explain the choice and the meaningful weakness of the rejected alternative; do not ask the user to choose merely to transfer the design responsibility.

## 4. Prove a representative slice

Develop the chosen hero, a content-dense section and a real functional component, such as a form, filter or navigation menu. These should demonstrate the typography, imagery, spacing, hierarchy and interaction language before it spreads to every page.

Inspect the actual desktop and mobile renders, including representative long or translated copy. A convincing hero with an unreadable service section is not a validated direction. Correct weak proportions, generic copy, unsuitable images and unfinished component states now, rather than relying on later decorative polish.

## 5. Review before generalizing

Use an independent reviewer when available and appropriate under `AGENTS.md`. Give the reviewer the brief, rendered slice and selected references before the implementation's design rationale, so the rationale does not replace their judgment. If independent review is unavailable, perform an explicit self-review and describe it honestly.

Request the few highest-impact findings with visible evidence and an actionable correction. “Make it premium” is not actionable; “the project evidence is buried below two screens of generic introduction; move it beside the proposition and shorten that introduction” is. Separate observed defects from aesthetic preferences.

Apply the selected corrections and inspect the updated render before generalizing. If the direction remains weak, revise the composition rather than accumulating effects. Keep the loop focused on substantive issues instead of endless alternative generation or arbitrary numerical design scores.

## 6. Complete and verify the experience

Extend the validated language across the required content and routes, maintaining consistency within the brand. For unrelated brands, reuse accessible behavior without automatically cloning presentation.

Apply the main skill's complete desktop/mobile, language, component-state, keyboard, loading, preloader, transition and reduced-motion checks. Review whole pages and journeys, not only isolated sections. Functional correctness and visual quality are separate judgments: passing a build or removing prohibited ornament establishes neither a coherent composition nor user satisfaction.

Keep reference observations, choices, corrections and remaining limitations in the normal brief or handoff, not a process file for every page. Report what was actually rendered and tested. Do not call an unobserved visual or interaction requirement verified, and do not promise that this workflow guarantees a successful first proposal.
